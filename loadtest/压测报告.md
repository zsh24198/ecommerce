# 秒杀接口压测报告

> 接口：POST /api/v1/seckill/activities/{activity_id}/buy  
> 日期：2026-10-16  
> 环境：4核8G 单机（Go server + MySQL8 + Redis7 + Kafka KRaft + k6 同机）  
> 工具：k6 v0.x  
> 活动配置：stock=100, limit_per_user=1

---

## 一、测试目标

验证秒杀链路在高并发下的三大核心能力：

1. **零超卖**：Redis 原子预扣保证不超卖
2. **一人一单**：同一用户只能成功抢购一次
3. **高性能**：QPS ≥ 500，p99 < 200ms

---

## 二、测试脚本修正

压测前对 `loadtest/seckill.js` 做了 3 处修正：

| # | 问题 | 修正 |
|---|------|------|
| 1 | token 按 `__VU % tokens.length` 固定绑定，500 VU 只用到 500 个用户，被用户限流(2/s)拦截 80% | 改为 `Math.floor(Math.random() * tokens.length)` 随机轮转 |
| 2 | code=5022（已购买）被计入 syserror_count，污染异常率 | 新增 `alreadybought_count` Counter，5022 归入"非失败"类 |
| 3 | k6 默认把 HTTP 429（限流）计入 http_req_failed，导致 100% 失败误报 | 用 `http.expectedStatuses({min:200,max:299}, 429)` 将 429 视为正常响应 |

```javascript
stages: [
  { duration: '30s', target: 50 },    // 预热
```

- 峰值并发：500 VU

## 七、结论

秒杀链路在 500 VU、1381 QPS 的高并发压力下：

1. **零超卖**：Redis Lua 脚本原子预扣库存 + 用户标记，100 件库存精确售罄，无超卖
2. **一人一单**：重复购买请求被 5022 拦截，无重复订单
3. **高性能**：成功请求 p99 仅 5.84ms，远低于 200ms 目标
4. **零异常**：syserror_count=0，http_req_failed=0%
5. **限流有效**：三层限流（IP→用户→全局）拦截了 99.96% 的超额请求，保护后端不被击穿

系统在 4核8G 单机环境下表现稳定，秒杀核心架构设计验证通过。
